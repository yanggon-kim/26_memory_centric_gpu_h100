## Terms used in this chapter

The handbook glossary is in [README.md](README.md). The terms this chapter leans on most:

| term | meaning |
|---|---|
| CU | compute unit, AMD's equivalent of an NVIDIA streaming multiprocessor (SM) |
| XCD | accelerator complex die; MI300X, MI325X and MI350X each have 8 |
| SE | shader engine; a group of CUs inside an XCD with its own workgroup dispatch. MI350X has 4 per XCD (`plan.py` `HW['mi350x']['se_per_xcd'] = 4`) |
| SH | shader array, a sub-group inside an SE (one bit of the CU key below) |

| R(n) | decode latency ratio T(n)/T(full), ms per decode step at n CUs over the same at the full device |
| B_CU | HBM bandwidth per CU = HBM bandwidth / CUs in use ("bandwidth per SM") |
| MLP | memory-level parallelism: HBM reads in flight |
| `wvSplitK` | vLLM's ROCm skinny-GEMM kernel used for batch-1 linear layers; about 81% of decode kernel time on MI350X |
| balanced(n) | the largest CU count ≤ n that gives every SE of every XCD the same number of CUs; on MI350X a multiple of 32 (`plan.py` `balanced()`) |

| E0–E8 | experiment IDs of the compute-vs-bandwidth (cubw) follow-up, defined in `docs/amd/compute_bandwidth_followup_20261026.md` |
| block | one GPU lane holding one acquisition of every cell, so comparisons are paired within a GPU |
| observational | a timing that is not clock-qualified; no MI350X job passed the clock gate |

## Introduction

### Why MI350X

Plan 2.0 (`docs/shoreline_aware_research_plan_2.0.md`) asks how much compute memory-bound LLM decode needs
relative to memory bandwidth. On AMD the proxy is to restrict CUs with `HSA_CU_MASK` and measure how decode
slows. The two earlier cohorts (MI300X, MI325X) share one CU layout and differ only in HBM. MI350X changes both.
It has fewer CUs and more bandwidth, so each CU must carry much more HBM traffic.
Source: `docs/amd/mi350x_campaign_plan_20261102.md` §1.

### Hardware differences

Vendor specifications as recorded in `docs/amd/mi350x_campaign_plan_20261102.md` and
`scripts/amd/cohort_index.py` (`HW`); measured values from E4 `seqread4g` at the full device:

| | MI300X | MI325X | MI350X |
|---|---:|---:|---:|
| architecture | gfx942 | gfx942 | **gfx950** |
| CUs (XCDs × CUs per XCD) | 304 (8 × 38) | 304 (8 × 38) | **256 (8 × 32)** |
| SEs per XCD | 4 | 4 | 4 |
| CUs per SE at the full device | 9,10,10,9 (unequal) | 9,10,10,9 | **8,8,8,8 (equal)** |
| LDS per CU | 64 KiB | 64 KiB | **160 KiB** |
| HBM peak | 5.3 TB/s | 6.0 TB/s | **8.0 TB/s** |
| HBM capacity | 192 GB | 256 GB | 288 GB |
| peak B_CU | 17.4 GB/s | 19.7 GB/s | **31.2 GB/s** |
| measured seqread4g at full device | 4563.5 GB/s | 4950.1 GB/s | 6416.2 GB/s |
| measured B_CU | 15.0 GB/s | 16.3 GB/s | 25.1 GB/s |

- The SE counts per XCD come from the placement CU keys. For MI350X see `docs/amd/mi350x_followup_plan_20261103.md`
  §B. For MI300X see the comment above `SE_LEVELS` in `scripts/amd/cubw/plan.py`.
- Toy job 496003 confirmed the device before any campaign: MI350X, gfx950, 256 CUs, 288 GiB. A gfx950 binary
  built on the login node ran correctly, and a vector add reached about 6.45 TB/s
  (`docs/amd/experiment_log.md`, 2026-11-02).
- The memory clock stayed at 2000 MHz in every MI350X job. The graphics (gfx) clock varied widely, so every
  timing is clock-confounded (details per job below).

### Two predictions the plan made before any MI350X data

From `docs/amd/mi350x_campaign_plan_20261102.md` §1:

1. **MLP prediction.** MI325X job 492957 suggested the CU-restriction penalty comes from fewer HBM reads in
   flight per CU. MI350X has 1.6–1.8× the bandwidth per CU. If the MLP explanation is right, a CU cut should
   cost *more* on MI350X at the same per-XCD fraction.
2. **Kernel-geometry prediction.** On MI300X/MI325X, `wvSplitK` launches one WG per CU, each using all 64 KiB
   of LDS. With 160 KiB of LDS, two 64 KiB WGs could fit per CU on gfx950. If the curve's shape changes, it is a
   software-geometry artefact. **This premise turned out false:** on gfx950 vLLM's `wvSplitK` asks for all
   160 KiB per WG, so it is still one WG per CU (#21).

### How a cubw job runs (short version)

The full pipeline is in [02_cubw_mi300x_mi325x.md](02_cubw_mi300x_mi325x.md). In brief, from `scripts/amd/cubw/submit.sh`:

1. `submit.sh <kind> mi350x <time> [plan.py args]` refuses to run with uncommitted changes under `scripts/`.
2. It freezes a read-only release snapshot `$WORK/cubw_release/<commit>`.
3. It writes an immutable plan `$WORK/cubw_plans/mi350x_<kind>_<date>_<commit8>.json` with `plan.py`.
4. It dry-runs every lane without a GPU, then calls `sbatch cubw.sbatch` on the plan's partition.
5. Inside the job, `cubw.py` runs one lane per GPU and journals every step to `journal/L<i>.jsonl`.
6. An `auto` plan runs the pilot stage, then `analyze.py gate` writes `gates.json`, then the production stage.
   Steps whose gate is false are journaled as `not_run`.
7. At the end `analyze.py report` writes `analysis/summary.md` and `cubw_tables.json`, and the root is hashed
   (`SHA256SUMS`).

The statistics (from the plan's `statistics` block): 3 warm-ups and 10 trials per acquisition. R(n) is a
ratio of means. Its 95% CI comes from 10,000 bootstrap draws (seed 20261018) that resample blocks, then
trials inside each block. A level would be "qualified non-inferior" if the upper 95% CI of R(n) ≤ 1.05 **and**
the pooled clock gate passed. The clock gate needs max/min of in-window gfx and memory clocks ≤ 1.05. No MI350X
job passed it, so every result is labelled `observational_clock_confounded`.

### The cohort rule

**Cohorts are never pooled.** MI350X is a third, separate cohort. Its results are never averaged or fitted
together with MI300X or MI325X. A comparison across cohorts is made only at matched per-XCD CU fractions, with
each cohort's own full device = 1, and is labelled as such.

- The rule is stated in `docs/amd/mi350x_campaign_plan_20261102.md` and in every published folder's `cohort.json`.
- `scripts/amd/cohort_index.py` (CPU only) makes the cohort explicit. It reads the cohort from each folder's
  `launch_plan.json` (`cohort`), or else from the folder name. It writes:
  - `results_published/<folder>/cohort.json` (cohort, GPU, architecture, CU count, bandwidth per CU);
  - `results_published/cohorts.json` (machine-readable index);
  - `results_published/COHORTS.md` (human-readable, grouped by cohort, with the reviews that cite each folder).
- It was added with cubw v1.5 (commit 09178c91; `docs/amd/experiment_log.md` 2026-11-03).

- **How it was run:** `submit.sh pilot mi350x <time> --smoke`. The time limit is not stated in the reviews. The

  submitted at the same time and held until this smoke was reviewed (`docs/amd/experiment_log.md`).

- **What was measured and how it was analysed:**
  - Placement: `svc_bench_gfx950_v3 --mode placement` under each mask. Each WG records `HW_REG_HW_ID` and
    `HW_REG_XCC_ID`. The count of distinct physical CUs must equal the request, with per-XCD counts within 1.
  - Decode: ms per step (HIP-event time) for Qwen2.5-32B-Instruct; outputs compared by digest.
  - Leak test v2: the v4.1 `cuprobe` runs on the CUs *not* given to the decoder (n..255). Each probe WG holds a
    full CU of LDS (160 KiB) and counts completed WGs per physical CU. Per CU c,
    r_c = rate beside X / rate alone and q_c = r_c / median(r_c). The positive control is a second probe that
    overlaps 8 of the probe's CUs. It must flag ≥ 4 CUs with q_c < 0.85, or the test is "insensitive" and fails.

- **Results:** (`results_published/amd_20261102_mi350x_cubw_v1_4_smoke_job496073/summary.md`, `preflight.json`)

  Placement was exact and even across XCDs:

  | mask | CUs | per XCD |
  |---|---:|---:|
  | full device | 256 | 32 |
  | 0–191 | 192 | 24 |
  | 0–127 | 128 | 16 |
  | competitor 192–255 | 64 | 8 |

  Single-acquisition decode (pilot values, not production estimates):

  | n | 256 | 192 | 128 | 128, kernel sized for 128 |
  |---|---:|---:|---:|---:|
  | ms/step | 12.23 | 14.72 | 14.51 | 15.40 |
  | R (pilot) | 1 | 1.204 | 1.186 | — |

  E4 rows at 128 vs 256 CUs: streaming read 0.891 (`seqread4g`), ILP-8 read 0.757, ILP-1 read 0.680, FMA 0.631,
  pointer-chase latency 0.991.

  Other findings:
  - **Decode works.** 5 runs gave 1 output digest, identical to the MI325X digest (`8fb99b67…`).
  - **Clocks:** memory 2000 MHz constant; gfx 1547–2202 MHz (pooled ratio 1.42).
  - **`wvSplitK` on gfx950:** 81.5% of decode kernel time. It launches **256 WGs, each with 160 KiB of LDS**, so
    one WG fills a CU, as on gfx942.
  - **Counters:** FETCH_SIZE and TCC_EA0_RDREQ_LEVEL runs completed. FETCH_SIZE is not validated on gfx950
    (preflight 0.50×).
  - **Leak test v2 is insensitive.** The positive control flagged **0** CUs at both n = 192 and n = 128, and
    every q was 1.000. On MI210 and MI325X the same control had flagged exactly 8.

- **What it means:**
  - The port works on gfx950. No port bug blocked the campaign, so 496074 was released unchanged.
  - The plan's "two WGs per CU" premise fails: vLLM still runs one full-LDS WG per CU.
  - Under the pre-registered rule, an insensitive leak test fails `leak_ok_v2`. So E3-minimal would not be
    released in the campaign. Other experiments were unaffected.
  - The review proposed a cause, untested at the time: with 160 KiB per probe WG, probe and foreign WGs cannot
    share a CU. If the dispatcher hands each launch's WGs to CUs in a fixed pattern, completion counts per CU
    are uniform by construction. #24 confirmed and extended this.

    - `boundary_level` is the argparse default, and the smoke has no E8.

    `COHORTS.md` repeats the `cubw_v1.2` label. The code that ran is the v1.4 release e7116c1f.
  - The `summary.md` E2 heading says "T(n)/T(304)"; on this cohort the denominator is T(256).

    - **E3-minimal:** in blocks 0–4: n ∈ {192, 128} × {absent, mem50, mem100, arith100}, plus an inactive control

    - **`e6_decode`:** in blocks 3–7, Qwen32B at each fine level below 256 with `CUBW_CU_COUNT_OVERRIDE=n`

    - E4 service curves at the 5 nominal levels plus the competitor mask, 3 acquisitions (339 steps);

    - at 256, the boundary 168 and 80: Qwen7B B8 decode and Qwen32B prefill;
    - at 256 and 168: Qwen32B C16384, Mistral-7B B1, and Qwen32B matched energy (10 trials × 2047 decode ticks).

    changes are not authorized).

- **How it was run:**
  - `submit.sh auto mi350x 03:45:00 --campaign`, submitted held behind the smoke and then released.
  - Binaries `svc_bench_gfx950_v3` and `_v4`.
  - The plan estimated a 2.95 h longest lane (10,630 s) and about 35.9 units. The job used 1 h 09 min.

- **What was measured and how it was analysed:**
  - **E2:** R(n) = T(n)/T(256), paired by block, with a bootstrap 95% CI (see the introduction).
  - **E4:** native microbenchmarks under each mask: streaming read, ILP 1–16, grid size, stride, gather, pointer
    chase, cache reuse, FMA, MFMA. Each is reported as a ratio to 256.
  - **E5/E6 kernel traces:** `rocprofv3 --kernel-trace` of graph-mode decode. `e6_kernels.py` keeps dispatches
    inside the decode NVTX ranges and aggregates per kernel: share of kernel time, mean duration, grid, LDS, and
    duration ratio to 256. Traces carry 4–10% instrumentation slowdown (`summary.md` E5).
  - **E6 shapes:** `e6_shapes.py` times the five Qwen32B weight shapes at batch 1: qkv, o_proj, gate_up, down,
    lm_head. Weights rotate over ≥ 1 GiB of copies, so every call streams from HBM. Variants:
    - `wvsplitk_dev`: sized by the device CU count, which is what vLLM launches;
    - `wvsplitk_n`: sized for the mask;
    - `linear`: hipBLASLt/rocBLAS;
    - `llmm1`.
  - **E6 counters:** rocprofv3 `--pmc` on `e6_shapes.py --light`. `e6_counters.py` averages the 3 timed
    dispatches per shape and variant. Mean HBM reads in flight = TCC_EA0_RDREQ_LEVEL / GRBM_GUI_ACTIVE.
  - **`e6_decode`:** `scripts/sitecustomize.py` patches `vllm.utils.platform_utils.num_compute_units` when

### Part A — leak test v3: design, and why it was insensitive

**Why v2 failed** (496074 raw `e1_leak_v2/*/competitor.jsonl`, per the pre-registration §A):
- Alone, the v4 probe completed between 506,264 and 506,282 WGs on every one of its 64 CUs. That near-identical
  count is the signature of a fixed per-launch assignment: 2048 WGs per launch, 32 per CU.
- Beside the positive control (8 shared CUs), the probe kept its counts on the shared CUs (about 519,000). The
  *co-runner* was starved there instead: 11,767–14,266 WGs on the shared CUs vs about 496,000 elsewhere.
- So on gfx950, a completion count cannot reveal a foreign WG on a probe CU, whichever side wins the CU.

**The v3 probe** (`svc_bench_v5.hip --mode cuprobe_t`, kernel `k_cuprobe_t`):
- 256 threads, no LDS.
- Each thread runs a dependent chase through an L2-resident 256 KiB ring (65,536 entries), plus 4 FMA chains,
  for 500 iterations.
- Thread 0 adds the WG's residency (`wall_clock64()` end − start, a constant-rate clock) and one completion to its
  physical CU's slot.
- Per-CU speed s_c = completions / summed residency (`analyze.py` `cu_speed`).
- The idea: a foreign WG co-resident on a probe CU competes for SIMD issue and the vector-memory path, so it
  lengthens residency there. With no LDS in the probe, a full-LDS WG such as `wvSplitK` *can* co-reside.

**Rule** (`leak_ok_v3`; `analyze.py` reuses `leak_v2_eval` on s_c):
- q_c = (s_c beside X / s_c alone) / median over c of that ratio.
- Every run must cover all 256 − n probe CUs.
- Natives are co-runners on 0..n−1 (mem100, arith100).
- Positive controls share 8 probe CUs (0..n+7): FMA, streaming read, and the v4 full-LDS probe.
- **Sensitive** iff each positive flags ≥ 4 CUs with q_c < 0.85.
- **Pass** iff sensitive and, for every decoder run, min q_c ≥ (lowest native min q_c) − 0.05.
- Levels 192 and 128 on two GPUs (L0, L1), suite order randomized.
- `release_e3_minimal_v3` = placement, lifecycle, outputs and `leak_ok_v3`. Only then would E3-minimal run: n ∈
  {192, 128} × {absent, mem50, mem100, arith100}, 5 blocks, plus one inactive control.

**Result:** insensitive on both GPUs at both levels. Every positive control flagged 0 of 8 shared CUs. Native
and decoder runs had min q ≥ 0.96 (`gates.json` `leak_v3`).

**Why it was insensitive** (from the #23 raw residency, `docs/amd/mi350x_followup_smoke_review_20261103.md`):
- The memory co-runner did lengthen residency on exactly the shared CUs, but only by about 7%, under the 15%
  flag threshold.
- The FMA co-runner did not put the shared CUs among the slowest.
- Against a full-LDS WG — how `wvSplitK` occupies a CU — the probe wins the CU and the foreign kernel starves
  (30k–44k WGs vs a 496k median). The probe sees nothing.
- So on gfx950 the intruder, not the probe, pays. A probe sitting on its own CUs cannot reveal a `wvSplitK`-like
  intruder.

E3 stayed blocked. **Later revision:** leak test v4 (svc_bench_v6 start-delay probe; jobs 499331/499332) was
sensitive and passed 16/16, and E3 then ran on MI350X (`docs/amd/mi350x_leak4_review_20261104.md`).

### Part B — the shader-engine hypothesis H_SE

**What was known before the job** (pre-registration §B):
- **vLLM's `wvSplitK`** (CPU reading of `/app/vllm/csrc/rocm/skinny_gemms.cu` in the container):
  - it launches `grid = CuCount` WGs, each with 16 waves and all 160 KiB of LDS, so one fits per CU;
  - each WG strides through output rows in rounds of `CuCount × waves × YTILE`.

  The host-side rounds and waves do **not** explain the pattern. For example, o_proj gets the same
  configuration at 192 and 184 (YTILE 2, 14 waves, 1 round) but runs 1.02× vs 1.55×.
- **Placement** (496074 `e1_placement` CU keys): contiguous masks interleave over XCDs, then over each XCD's 4
  SEs. Active CUs per SE per XCD:

  | n | 256 | 232 | 208 | 192 | 184 | 168 | 152 | 128 |
  |---|---|---|---|---|---|---|---|---|
  | CUs per SE | 8,8,8,8 | 8,7,7,7 | 7,7,6,6 | 6,6,6,6 | 6,6,6,5 | 6,5,5,5 | 5,5,5,4 | 4,4,4,4 |
  | balanced? | yes | no | no | yes | no | no | no | yes |
  | balanced(n) | 256 | 224 | 192 | 192 | 160 | 160 | 128 | 128 |

  The levels where a sized kernel reached full speed (256, 192, 128) are exactly the balanced ones.
  `balanced(n) = n − n mod (8 XCDs × 4 SEs) = n − n mod 32` (`plan.py`).

**H_SE (as pre-registered):** with one 160 KiB WG per CU, the dispatcher spreads a launch's WGs over the SEs in a
way that does not follow the active-CU count per SE. Where SEs differ, some CUs get a second WG. It runs only after
the first finishes, so the kernel takes up to about two WG times.

**Predictions and pass criteria:**

| prediction | test | pass criterion |
|---|---|---|
| **P1** dispatch | `e6_dispatch`: 5 trials, 160 KiB LDS, 16 waves, grid = n under mask n | (a) at 256, 192, 128: max 1 WG per CU and 0 serialized in every trial; (b) at ≥ 3 of the 4 strongly unbalanced levels (208, 184, 168, 152): max WG/CU ≥ 2 and serialized > 0; (c) grid = balanced(n) under mask n gives max 1 WG/CU at every level. The no-LDS control is recorded, not judged |
| **P2** shapes | `wvsplitk_c<balanced(n)>` vs `wvsplitk_n` under mask n, 3 acquisitions | at each unbalanced level, the balanced size is faster for ≥ 4 of 5 GEMM shapes |
| **P3** decode | `e6_balanced`: Qwen32B with `CUBW_CU_COUNT_OVERRIDE = balanced(n)` under mask n, paired by block with E2 at n and 256, 8 blocks | R_balanced(n) < R_e2(n) at every unbalanced level, **and** R_balanced(208) (size 192) within ±0.03 of R_e6_decode(192) from the same job |

Verdict rule: **supported** if P1 and P3 pass; **refuted** if P1 fails; if P1 passes and P3 fails, the decode
cause is still open.

### The dispatch-probe method in detail

The dispatch probe is `svc_bench_v5.hip --mode dispatch` (kernel `k_dispatch`). It mimics a `wvSplitK` launch
and records where and when each WG ran.

**Launch shape** (`plan.py` `dispatch_suite`):
- `--blocks g --threads 1024 --bytes 1073741824 --trials 5 --warmups 2`, under `HSA_CU_MASK=<gpu>:0-<n-1>`.
- `--threads 1024` gives 16 waves, like `wvSplitK`.
- `--lds` defaults to the device's LDS per CU (163,840 bytes = 160 KiB on gfx950), so one WG fills a CU's LDS.
  Above 64 KiB the program raises the kernel's dynamic-LDS limit with `hipFuncSetAttribute`.
- For each level n, the grids run are g ∈ {256, n, balanced(n)} (deduplicated). There is also a no-LDS control:
  g = n with `--lds 1`, a 1-byte LDS request, so WGs can co-reside.
- The 1 GiB buffer is split evenly: each WG streams its own contiguous chunk of 1 GiB / g with `float4` loads.
  Total bytes are fixed, so a smaller grid means more bytes per WG.

**Per-workgroup record** (one record per WG per trial):
1. **Start.** At entry, every thread reads `wall_clock64()`. The value is kept as t0.
2. The WG streams its chunk, then `__syncthreads()`.
3. **End and CU key.** Thread 0 writes `rec[3b] = cu_key()`, `rec[3b+1] = t0`, and `rec[3b+2] = wall_clock64()`.
4. **Per-WG CU key**, from hardware registers:
   - `HW_REG_HW_ID` gives the CU id (bits 8–11), SH (bit 12) and SE (bits 13–15);
   - `HW_REG_XCC_ID` (low 4 bits) gives the XCD;
   - key = `xcc<<8 | se<<5 | sh<<4 | cu`, printed as `key_layout` in `out.json`.

   This is the same key as the placement probe, so keys are physical CUs, not logical mask indices.
5. **Wall clock.** `wall_clock64()` runs at a constant rate. The device reports it in `hipDeviceAttributeWallClockRate`;
   the outputs show `wall_clock_khz: 100000`, so one tick is 10 ns. It does not follow the varying gfx clock, so
   start/end times are comparable across WGs and CUs. On the host, times are converted to ns relative to the
   earliest WG start in that trial.
6. **Kernel time** is the HIP-event time around the launch (`kernel_ms`).
7. The record buffer is filled with `0xff` before each trial. `check_passed` is true only if every WG wrote its
   record ("every workgroup recorded").
8. Output: one JSON line with `trials[].wg = [[cu_key, start_ns, end_ns], …]` per trial
   (e.g. `$WORK/results_amd/amd_20261103_mi350x_cubw_v1_auto_job497082/e6_dispatch/n128_g128/a0/attempt1/out.json`).

**Summary statistics** (`analyze.py` `dispatch_summary`), computed per trial:
- `cus_used`: distinct CU keys that ran ≥ 1 WG.
- `max_wg_per_cu`: the largest number of WGs on one CU.
- `cus_with_2plus`: CUs that ran ≥ 2 WGs.
- `wg_per_se_xcd0`: WGs per SE on XCD 0 (key >> 8 = 0, SE = key >> 5 & 7).
- **`serialized_wgs`:** for each CU, its WGs are sorted by start time. Each consecutive pair (WG i, WG i+1) is
  counted as serialized if **start(i+1) ≥ end(i) − 100 ns**. The second WG starts no earlier than 100 ns before
  the first one ends, so it waited for the first to leave the CU. The count is summed over CUs.
  - Two WGs that co-reside start almost together, well before the first ends, so they are not counted.
  - The 100 ns tolerance (10 ticks) absorbs launch jitter.

Across the 5 trials:
- `kernel_ms_median` is the median;
- `serialized_wgs_mean` is the mean (hence fractional values such as 6.4);
- `cus_used`, `max_wg_per_cu` and `cus_with_2plus` are maxima over trials;
- `wg_per_se_xcd0` is taken from trial 0 only.

**How to read it:** with g = n under mask n, an ideal dispatcher puts exactly one WG on each active CU. Then
`cus_used` = n, `max_wg_per_cu` = 1 and serialized = 0. A serialized WG means one CU ran two full-LDS WGs back to
back while some other active CU ran none. The kernel then lasts about two WG times.

### The B_CU table without the dispatch artefact

From `docs/amd/mi350x_followup_review_20261103.md` §3. Once WGs no longer serialize, decode time depends on the
balanced CU count actually doing the work. "B_CU needed" = 8.0 TB/s peak / CUs doing the work.

| CUs doing the work | fraction | B_CU needed (8.0 TB/s peak) | R |
|---:|---:|---:|---:|
| 256 | 100% | 31.2 GB/s | 1.000 |
| 224 | 88% | 35.7 GB/s | 1.004 |
| 192 | 75% | 41.7 GB/s | 1.009 |
| 160 | 63% | 50.0 GB/s | 1.067 |
| 128 | 50% | 62.5 GB/s | 1.168 |

### What it means

- **H_SE is supported on MI350X.** `wvSplitK` launches one 160 KiB WG per CU. When active CUs per SE are unequal,
  the dispatcher does not follow them: some CUs get two WGs, which serialize. That roughly doubles the time of the
  kernel that carries about 81% of decode.
- **The 16–25% step of #22 was mostly this artefact, not a bandwidth limit.** With the kernel sized to
  balanced(n), MI350X decodes within 1% of full speed down to 75% of its CUs (192). Below that, the cost rises
  smoothly with B_CU: 1.07 at 160 CUs (50 GB/s per CU) and 1.17 at 128 (62.5 GB/s per CU).
- **Practical rule (MI350X):** size `wvSplitK` to the largest multiple of 32 ≤ the active CUs. For example,
  restrict to 208 CUs and size for 192.
- **Earlier result revised (stated explicitly):** #22's "the sized kernel fails at 208/184/168/152" was a
  dispatch artefact of sizing to an unbalanced n.
- **Later revision on MI300X** (499334, `docs/amd/mi300x_se_review_20261105.md`; summarised in
  `docs/amd/compute_bandwidth_followup_results_20261103.md` §5):
  - The pre-registered H_SE verdict is *refuted on MI300X*: the full device (9,10,10,9 per SE) does not serialize.
  - Reduced unbalanced masks do serialize, as on MI350X.
  - Balanced sizing gives R 0.993–0.998 down to 128/304 CUs. This revises 492956's "resizing is slower at every
    level": those sizes were all SE-unbalanced.
  - Both cohorts decode at full speed up to about 42 GB/s per CU.

### Failures and caveats

- **Clock confounding:** pooled gfx ratio 1.58 (gate ≤ 1.05). No result is a qualified non-inferiority claim.
- **Narrow scope:** the dispatch probe ran on one GPU (L2), and decode used one model (Qwen32B B1/C4096).
- **Leak v3 insensitive,** so E3 did not run in this job. It was resolved later by leak v4 (499332).
- **E2 CIs differ between jobs.** The #24 E2 CIs are much narrower than #22's at the same levels (e.g. 232:
  [1.230, 1.236] vs 1.19–1.32). Both use the same 8-block bootstrap. The reviews do not discuss why the
  block-to-block spread was smaller in #24. Not recorded.
- **Generator scripts not found:** `hse_judgment.json` and `e6_kernels_balanced.json` are cited by the review,
  but no script named for them was found in `scripts/` (searched for the file names). `e6_kernels_balanced.json`
  has the `e6_kernels.py` output format.
- **Labels:** `summary.md` headings still say "T(n)/T(304)" and "ratio to 304"; here they mean 256.
- **Two counts that differ by definition, not by data:**
  - "CUs with ≥ 2" (`cus_with_2plus`) is the maximum over 5 trials, so it can exceed the mean serialized count;
    e.g. 208: 10 CUs vs 8.0 serialized.
  - "WG per SE (XCD0)" is from trial 0 only. Per-SE patterns quoted in the reviews (e.g. 6,7,6,7 at 208) can
    differ in order from this job's trial 0 (7,6,7,6).
- **E3 pilot** (one acquisition, pilot-labelled, no isolation proof): at 192, mem100 1.19, arith100 0.94,
  memory/arithmetic 1.26 (`summary.md`).
