## Research question

At fixed model quality and latency targets, when does mixing prompt chunks with decoding improve serving? After each allocation receives appropriate kernel and scheduler tuning, which workloads still tolerate fewer CUs or respond strongly to memory service? A second deployment of interest assigns prefill and decode to separate workers. The outcome can favor full arithmetic throughout, favor specialization only for a subset, or identify a broader opportunity.

[SARATHI](https://arxiv.org/abs/2308.16369) combines prefill and decode rows in dense linear operations that use the same weights. Each request still attends to its own context. [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal) prioritizes ongoing decodes and uses a token budget for prompt chunks. The budget trades prefill efficiency against time between generated tokens. Our [previous AMD serving study](goal_followup_results_20261107.md) already enabled chunking. At concurrency eight, restricted allocations achieved roughly 72%, 78% and 80% of stock output throughput on MI300X, MI325X and MI350X. Those finite closed-loop trials motivate measuring the actual schedule, retuning the budget, and replaying identical work. See the [runner](../../scripts/amd/goal/serve_mix.py), [competition protocol](goal_g5y_plan_20261109.md), and [fixed-area objective](../area_allocation_mathematical_model_v0_20261105.md).

## 1. Replay identical batches and measure prefill headroom

Construct replayable engine iterations with matched request tokens, KV state, decode positions, prefix lengths and kernel path. Restore or reconstruct the state outside the timed window. Verify the executed token counts from the scheduler or model runner. An isolated linear-kernel benchmark is useful additional attribution when whole-step replay succeeds. If engine replay is unavailable, use a controlled admission/barrier harness and report the achieved fidelity.

Suggested initial decode widths are 1, 8 and 32 requests, with short and long resident contexts such as 1K and 8K where memory permits. Add 0, 64, 256, 512 and 1024 fresh prefill tokens, refining near transitions and recording effective kernel shapes and padding. Hold prefill prefix length fixed within each sweep. Measure elapsed GPU step and scheduler wall time, and profile representative linear and attention kernels separately from timing runs. For decode width N, context S and allocation a, report the largest tested C satisfying T(N,C,S,a) ≤ 1.05 T(N,0,S,a). Show the entire curve, uncertainty, nonmonotonic points and the common absolute deadline. Report an interval or open boundary when the sweep cannot resolve the crossover. Compare full and reduced masks first at identical settings, then with each mapping tuned.

## 2. Compare three scheduling policies under identical offered traffic

Replay whole prefills served separately, chunked prefills served separately, and chunks mixed with decode. Verify each policy with execution logs. A large token budget can still permit mixing. Where the installed engine lacks a policy switch, implement a small reproducible scheduler control and validate pure and mixed step types. Document unavoidable backend or priority changes and qualify such comparisons. Include pure-prefill and pure-decode anchors.

Use open-loop arrivals and identical request IDs, lengths, contents and timestamps across treatments. Sweep actually computed prompt tokens per decode tick from below one through balanced and prefill-heavy demand. Exercise smooth and bursty arrivals at matched mean rates and request sets. Vary load across the saturation point. Compare common token budgets first, then give each policy and allocation the same tuning opportunity on development traces. On held-out traces report sustainable request rate and SLO-compliant goodput, output tokens/s, p50/p99 TTFT and inter-token latency, failures and energy per output token. Define request-level compliance and the warmup, measurement and drain windows. Include offered arrivals, queue growth and incomplete requests so overload cannot improve reported goodput. Use enough independent requests and repeated traces to support tail estimates, or show the sampling limitation.

## 3. Separate resident history from fresh prefill

First hold fresh suffix, output lengths and arrivals fixed while varying warmed prefix length from zero to a feasible long context. Next hold the total context and tokens fixed while varying warm-hit versus cold-miss state. Use independent prefixes across requests except in a declared sharing treatment. Verify prefix hits and actually recomputed tokens in engine records. Exclude cache construction from steady-state timing and report warmup cost for the cold-start comparison. Measure attention latency, executed fresh tokens, logical KV demand, observed cache service and validated HBM bytes when available. Report both decode-only and mixed steps. Test whether the compute saved by prefix reuse coexists with substantial attention service for resident history. A software prefix-cache hit describes reused KV state and provides no direct measure of its SRAM residency.

## 4. Extend the disjoint-CU competition tests to mixed steps

Reuse the placement-qualified AMD probes, mappings, positive/negative controls and versioned service benchmarks. Select decode-only, light-mix and heavy-mix iterations from experiment 1 and hold their request state and decoder placement fixed. Use competitor-absent, idle, memory-dose and arithmetic controls on an owned disjoint CU set. Record achieved competitor traffic, clocks, masks, placement checks and decoder latency for every treatment. Compare within a decoder mask first. Across masks, match achieved competitor dose where feasible. Report sensitivity and uncertainty against achieved traffic. Shared cache, fabric, power and HBM can all contribute. Above-stock bandwidth speedups remain analytical projections. Carry forward physical-counter validation and report an unavailable HBM counter as unavailable.

## 5. Compare colocated replicas with disaggregated workers

Reserve two comparable allocated GPUs and record peer topology and transport. At equal GPU count compare two colocated replicas with a tuned router against one prefill worker and one decode worker using a real KV transfer path. Run the split with a full decode worker and again with a restricted decode worker. Compare to the best tuned colocated allocation from experiment 2, retaining the stock colocated reference. Use the same model, precision, outputs, request trace and absolute SLOs. Test decode-heavy, balanced and prefill-heavy traffic under increasing open-loop load. Measure both queues, transferred KV bytes, transport latency and overlap where observable, sustainable goodput, tail latency, and whole-system energy per output token with both boards included and sensor scope declared. Include idle capacity of the paired worker in the accounting.

If a two-device engine or connector fails, diagnose and retry on a supported available route. As a fallback measure real KV-size transfers on the available link plus both worker service curves, and publish a clearly labeled modeled deployment comparison with its assumptions. Keep the real end-to-end case open with its exact blocker and resume command.
