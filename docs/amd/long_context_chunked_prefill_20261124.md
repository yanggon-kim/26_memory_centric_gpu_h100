# AMD handoff: where chunked prefill stops helping

Start here when the owner gives the execution prompt. Run all five measurement families on allocated AMD hardware and publish results on `amd/mi300x-phase0`. The objective is to identify where a tuned mixed scheduler improves serving and what limits the remaining decode work. Effective memory bandwidth can improve through fewer off-chip bytes, better cache/fabric service, more outstanding requests, or faster HBM. Distinguish these mechanisms wherever the counters permit.

## Starting evidence and reusable code

At commit `99e80ef5` the [campaign report](cp_campaign_results_20261118.md) covers Qwen2.5-32B/7B BF16, replay widths 1/8/32, decode contexts 1K and 8K, serving prompts up to 6144 and outputs up to 768. In full MI300X 32B tuned mixed runs at 2 requests/s (held-out seeds 201–203, decode-heavy), pure decode comprised 95.5–96.0% of steps and 87.9–89.5% of logged execution time. The latter includes synchronous executor overhead. Reuse one of those cases as a regression anchor. [SARATHI §§4–5](https://arxiv.org/html/2308.16369v1) motivates the shared-weight mechanism; its marginal decode cost differs from user-visible token latency.

Start with the [replay driver](../../scripts/amd/cp/cp_replay.py), [policy and step logger](../../scripts/amd/cp/cp_sched.py), [serving driver](../../scripts/amd/cp/cp_serve.py), [trace generator](../../scripts/amd/cp/cp_trace.py), [analyzer](../../scripts/amd/cp/cp_analyze.py), and [prior execution design](cp_campaign_design_20261118.md). The replay driver's default maximum length is 16384. Set the engine limit explicitly, check the pinned model revision's supported positions and attention window, and reserve positions for generated tokens. Verify the actual model, engine, kernel backend, KV precision, graph path, token budget and available KV blocks at runtime. Use the existing optimized single-GPU route on full MI300X with 32B first. Use 7B to reproduce selected transitions or explore a capacity-limited shape; label substitutions separately. Follow repository allocation and instrumentation controls. One allocated GPU suffices per case, including owned disjoint-CU competition. Independent cases may use additional allocated devices.

## Measurements

1. **Cost of chunking a long prompt.** With one request and no concurrent decoder, compare the exact same prompt whole against mixed-scheduler budgets 256, 1024 and 4096. Start at 1K and 8K, then 16K and 24K or 32K within the verified model limit. Use fixed token IDs, cold prefix state, equal model-length and KV settings, and one generated token to isolate prefill. Give the whole arm enough budget for the entire prompt and confirm the actual one-step execution. Measure TTFT, GPU elapsed time through the first output, chunk count, actual tokens per chunk, previous-prefix length per chunk, linear/attention time, and read/write traffic where observable. Report chunked/whole ratios at each length. For equal chunks of c tokens across k chunks, the sum of earlier prefix positions revisited is c*k*(k−1)/2. Treat that as logical demand; tiling and cache residency determine physical reads. Compare against measured traffic and quantify the contribution of smaller GEMMs and launch overhead as well.

2. **Separate growing decode attention from prefill attention.** Build decoder KV state outside the measurement window. Replay matched steps with active decode width 1 and 8 (32 where capacity permits) at the context lengths above. Add 0, 256 and 1024 fresh tokens from another request with a fixed prefill prefix. Independently change that prefix at one fixed decode context as a control. Record actual per-request positions, padding, backend and total step latency. Use roctx ranges and rocprofv3 on sampled steps in each regime, keeping ordinary timing separate. Attribute GPU intervals to shared linear layers (QKV/O/FFN), decode attention, prefill attention, KV update and other work. Verify roles from kernel/dispatch metadata and pure-decode/pure-prefill anchors. Report fused or unresolved time explicitly. Use per-iteration records and stratified profiling; report absolute milliseconds, fraction of GPU time and coverage. Compare hybrid time with decode alone and with separate execution of the same prompt chunk and decodes.

3. **Locate the pure-decode tail.** Generate 512, 2048 and 4096 output tokens from the same short prompt (e.g. 128 tokens), greedy with EOS ignored. First inject a second request just after first output, with either 128 or 8192 fresh input tokens. Then run matched open-loop traces under whole/separate, chunked/separate and chunked/mixed policies, sweeping at least a small and large mixed budget. Include an earlier balanced or prompt-heavy control. Match offered rates, seeds and arrival timestamps across policies; include a fixed-rate slice across output lengths and identify overload separately. Add a bursty-arrival repeat near the transition. Log actual fresh/recomputed and decode tokens, context, queue depth and step type. Report pure-decode fraction by count, by synchronous execution time, and by GPU-active time on profiled windows. Split steady arrivals from post-arrival drain. Report effective P:D from token sums, latency between outputs, TTFT, completion and SLO-compliant goodput. Use sufficiently long traces to distinguish single-request tails from steady service.

4. **Test effective memory service in the remaining work.** Select short/long pure-decode and mixed cells from 2–3. Compare useful FLOPs with validated physical DRAM read/write bytes in the same scope, compute achieved bandwidth against a matched streaming reference, and retain clean timing and clock telemetry. Validate the counter observation point on known-byte controls; pre-MALL and cache-interface counts must retain their actual labels. Earlier AMD physical-HBM validation was incomplete. If the counter remains unavailable, publish logical demand, measured service at the observable level and the corresponding inference limit. Reuse the [placement-qualified disjoint-CU protocol](goal_g5y_plan_20261109.md) to compare idle, arithmetic and at least two streaming doses at a fixed decoder mask, with recorded competitor throughput and placement. Test whether memory-service degradation changes long-context attention latency or throughput, controlling for shared clocks and fabric. Report evidence for memory sensitivity separately from any projection above stock bandwidth.

5. **Judge whether chunking helps serving in each regime.** Replay selected low-P:D, long-context, and long-uncached-prompt conditions under identical input traces on full hardware. Tune a small budget grid on development seeds and compare on fresh held-out seeds under common declared TTFT and inter-token limits. Include near-capacity and light-load conditions. Compare against the best whole/separate policy and retain per-request stalls and energy when qualified. Replicate a winning, losing or unresolved boundary on another available AMD cohort or the second model. Explain tradeoffs where chunking improves one metric at the expense of another. Rank the remaining bottlenecks for our architecture model by measured time and service sensitivity.

## Execution and return

Before the main acquisitions, publish a versioned design and smoke the short anchor, one long prompt and a genuinely mixed step. Use distinct run roots, pinned inputs, warmups, repeated clean trials and paired uncertainty intervals. Hold input content, cache state, arrival trace and comparison scope fixed for each contrast. Record output lengths and digests, numerical mismatches, actual peaks in KV occupancy, preemptions, timeouts, OOMs, compiler/capture failures and profiler overhead. If capacity is tight, reduce width first to preserve long context; if the route is unsupported, publish its blocker, adapt the route, and label the replacement. Keep a comparable on/off pair after any adaptation.

Push the implementation, configs, per-case status, compact step/counter data or retrievable raw archives with checksums, reproduction commands, and a final Markdown report. Include curves of chunked/whole prefill time versus prompt length, decode attention milliseconds/share versus resident length, pure-decode time share versus effective P:D, and SLO-goodput versus load. Give the measured context/output ranges and GPUs explicitly. For each measurement family record the supported conclusion, the strongest counterexample and any remaining gap. Checkpoint between stages and resume unfinished cases after interruptions. Return the branch, final SHA and report path.
