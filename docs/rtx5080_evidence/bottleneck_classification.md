# Bottleneck classification and uncertainty

Two distinct behaviors are established. The original eager Transformers decoder has extensive launch/control gaps; compiled StaticCache and vLLM greatly improve this reference. The optimized B1 vLLM decoder instead spends most profiled kernel time in weight GEMV. Its larger MLP GEMVs approach sustained DRAM throughput with little L2 reuse and long-scoreboard pressure. These software and kernel behaviors must not be conflated into a single memory-capacity problem.

At B1 the controlled vLLM C128/C1024/C4096 medians are 4.920/4.926/4.935 ms per batch decode step. At B8 they are 5.390/5.643/6.470 ms. This shows context-dependent overhead at higher batch; it does not by itself establish NoC saturation. A sampled long-context attention kernel uses 45% sustained DRAM and 23% SM throughput; unsaturated memory plus low occupancy makes a latency/concurrency/control explanation plausible, but exact causality remains unresolved.

Compiled StaticCache performs worse as context grows (B8/C4096 approximately 27.24 ms). The explicit full-capacity attention mask and backend are part of this software choice. Its timing is a reference for compilation/cache-policy behavior, not the strongest available baseline. The B16/C128 strict same-shape check fails and is excluded: sequence10 first differs at generated-token index2. Diagnostic eager logits tie tokens15/24 at10.625; compiled replay puts24 at10.6875. This supports sensitivity to small numerical changes near a tie. Returning diagnostic logits may alter fusion, so no compiler defect or harmlessness is claimed.

Async vLLM multi-model measurements use per-request first-to-last-token intervals. Their batch window can overlap later requests' prefill. Controlled in-process vLLM uses a verified all-request first-token barrier before CUDA-event/synchronized wall measurement and is the primary clean batch-decode timing comparison. All prompts are synthetic seeded uniform token IDs; no production-serving/general-quality claim follows from deterministic length checks.

B8/C4096 extended profiling confirms a backend/regime migration: two pure decode steps use BF16 WMMA GEMM for72.0% of busy kernel time, with split-KV attention21.2% versus4.1% at B1/C1024. This supports including larger-batch attention and arithmetic as counterexamples to compute trimming. It does not prove compute saturation or NoC pressure.

The final B8/C4096 attention counter sample reaches78.43% sustained DRAM throughput with33.626MB reads and3.18% L2 hits, corroborating materially increased KV movement. The selected QKV GEMM has7.06% Tensor activity; compute saturation is not established. Low occupancy/underfilled grid and memory delivery remain relevant. This is a weight-versus-KV pressure shift, not evidence for a NoC or cache-capacity bottleneck.
