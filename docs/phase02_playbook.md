# Future H100 Phase 0–2 execution playbook

This playbook describes the complete Phase 0–2 contract. Selected H100 bridge, energy, analytical reuse and partial native-trace steps have now been attempted; see `STATUS.json`, `results/case_manifest.json` and `docs/opportunity_report.md` for their disposition. For a new rental, follow `RENTAL_RESUME.md` first to select unfinished tasks; this file remains the full methodology. Begin with primary specification Sections 0 and 14. Establish evidence, including failures, before picking an architecture. The historical RTX study does not demonstrate H100 behavior, feasible SRAM area, or energy benefit.

## Phase 0: allocation and reproducibility gate

1. Record rental provider/instance, actual H100 SKU (SXM/PCIe/NVL), physical UUID, HBM size, SM count, clocks/power limits as observed, driver, toolkit, OS, CPU/RAM, free disk, storage throughput, network/transfer constraints, profiler permissions and rental deadline. MIG and multi-GPU studies need separately validated scope. Inventory may inspect other devices; execution must expose only the declared UUID.
2. Supply an existing compatible CUDA 13 toolkit and driver for the pinned torch/vLLM runtime. Do not silently select another PATH toolkit, install a system driver, or change clocks/power. Record `CUDA_HOME`, `nvcc`, `cuobjdump`, `ncu`, `nsys`, package freeze and imported CUDA runtime. Version equality is not ABI or H100 kernel correctness.
3. Run `inventory.py --check-cuda`; GPU targeting crosschecks CUDA/NVML UUID after PCI ordering. Stop on other compute processes. The file lock only coordinates these scripts. Record sharing/graphics and inspect concurrency during long runs.
4. Materialize the bridge smoke with its pinned revision. Resolve larger models once through HF metadata, record immutable SHAs and download bytes, then use local/offline paths. Review model licenses/gating. Templates are not evidence that weights are already available.
5. Inspect Accel-Sim/NVBit checkout pins and CPU regression evidence. Verify an actual H100 small native tracer capture and positive replay before expensive traces. Read `simulator_audit.md`; the H100 power model and our workload calibration are not established. Stock H100 config is132SM/SXM-like. Derive and preserve a distinct actual-SKU config (SXM/PCIe/NVL SM count, HBM capacity/interface/clock/bandwidth, cache and core clocks/L2) before timing calibration. A generic sm_90 replay with stock config proves parser/completion only, not SKU accuracy.

Gate: at least a correct GPU baseline and usable profiler route. If permissions, fitting, trace/parser or energy calibration fail, preserve explicit limitations and incomplete gates; do not fabricate a simulator or power result.

## Phase 1: staged fixed-precision baselines

The model registry starts with BF16 Qwen2.5 1.5B as a bridge, then 7B/14B/32B and Mistral 7B for a distinct dense head layout. Actual heads/layers/sliding-window fields are recorded from downloaded configuration. Do not hardcode that every family behaves like Qwen. Conditional Qwen3-30B-A3B may run timing/profile/trace after dense baselines within the same single-GPU/BF16 resource budgets; no additional approval is needed for that authorized model variation. Its official config has128experts,8selected/token,48layers and4KVheads ([source](https://huggingface.co/Qwen/Qwen3-30B-A3B/raw/main/config.json)); resolve and record the immutable revision. Routed-expert logical analysis requires its own validated adapter, and the shipped dense reuse script rejects it.

Each model starts B1/C128. Baseline stages are progressively bounded: bridge/7B/Mistral B1/4/8 × C128/1024/4096; 14B B1/4; 32B B1 × C128/1024. Initial 32B memory utilization 0.90 is a hypothesis about fit, not a guarantee. OOM stops the run and preserves failure. Review measured weight/KV/workspace/graph allocation before adding shapes. Never silently quantize, change dtype, increase allocated GPUs, or label a subset complete. Adjust a new recorded configuration if necessary.

Use `materialize_config.py --stage baseline` only after smoke passes. Run controlled vLLM timing before energy/profiling. At least three complete warmup sequences and three measured trials are required. The runner queues all requests, executes one prefill step, verifies every request has exactly one token/no prefix hit, synchronizes, then times exactly N−1 decode ticks. If the scheduler staggers prefill or produces empty ticks, the strict boundary fails; diagnose rather than repurpose an async timestamp interval as pure decode.

Retain GPU-event and synchronized wall separately; both include actual launch gaps, while wall includes scheduler/assertion overhead. Aggregate throughput numerator is B×(N−1), whereas latency is milliseconds per batch decode step. Fixed synthetic token prompts, greedy sampling, EOS ignored, no repetition penalty, BF16 KV and token digests are required. Full IDs allow independent comparison. Cross-GPU/kernel BF16 token differences require diagnosis, not an arbitrary tolerance that hides a mask/cache error.

After the controlled synthetic bridge, add a second workload from a public versioned dataset or explicitly versioned text. Save exact token IDs/tokenizer revision, length/truncation policy, sample selection and prompt hashes; use a separate workload/configuration label. The controlled vLLM runner now supports `workload_file`; `configs/representative_text_v1.json` and `configs/representative_b1_b4_c128.json` prepare four passages for B1/B4 C128. This route has not passed a GPU baseline. Rematerialize its old rental model path, validate prompt lengths/hashes, and preserve a distinct configuration label. Especially for MoE, uniform random prompts or repetitive greedy generations cannot establish representative expert routing/locality. Validate the adapted pure-decode/correctness boundaries before tracing and report expert selection with real prompt provenance.

Use StaticCache + `torch.compile` as a distinct software control. It removes dynamic cache concatenation and can reduce launch overhead; it does not create new SRAM hardware. The per-shape eager/compiled gate remains strict. Returning logits in diagnostics can alter fusion; preserve that qualifier. Filled versus preallocated cache length affects SDPA traffic. The historical B16 failure is unresolved numerical evidence, not proof that all larger shapes work.

Energy uses a separate long pure-decode sequence (start with 1024, explicitly extend to 2048 if the window is under 5 seconds). Sample at 20 ms, retain raw cumulative-counter delta, bracket-interpolated trapezoid power, timestamps, observed distinct readings/cadences, idle diagnostics, clocks and temperature. Scope is whole GPU board, no idle subtraction. Primary J/token is NA on missing sensors, short/cadence-inadequate windows or counter/power discrepancy over 10%. Agreement only provides an internal crosscheck; external absolute accuracy remains uncalibrated. Do not assume one sensor is true, multiply a counter by two, subtract idle power silently, or equate board energy with HBM/dynamic/static energy.

Profile a separate instrumented process. Discover actual kernels with Nsight Systems; query available H100 metrics before Nsight Compute. Select a small observed GEMV/GEMM/attention kernel set, bound launch counts, and separate profiler data from uninstrumented timings. For controlled vLLM pass `--external-profiler`; StaticCache uses profile mode. Inspect actual loaded sm_90/sm_90a cubins with the matching `cuobjdump`; record module/cubin hashes. Do not transfer RTX kernel names or SASS instruction evidence directly to H100. Use sufficient CUDA+NVTX events to prove selected launches are decode.

Existing-feature controls must document which optimized kernels actually use GQA/paged attention, fusion, CUDA graphs, async copies, TMA/WGMMA or cluster/DSM/multicast. Feature support alone is not an ablation. Build selective supported software controls or mark them unavailable; never claim a new fabric beats unmeasured Hopper facilities. Keep a larger-batch compute-active counterexample before proposing fewer arithmetic pipelines.

Gate: quantitative kernel/tensor classification distinguishing saturated bandwidth, latency/MLP, cache/NoC/issue and compute. Low tensor utilization or latency alone is insufficient. Report unknown counters as NA with reasons.

## Phase 2: traffic/reuse and native Hopper trace gate

Materialize logical configurations with explicit measured/SKU-verified L2 bytes and provenance; no RTX L2 default is inherited. Run `reuse_analysis.py` across LRU, pinned weights and prefix pinning, shared-prefix fractions, several capacities, block granularities (4 KiB/64 KiB/2 MiB) and recurrence warmups/steps. Metadata comes from actual safetensors headers and model layout. Only dense supported naming is accepted.

These are full-allocated-block synthetic fills with write-through/no-write-allocate, fully associative policies and declared access order. They are not actual GPU transactions, exact reuse distances, timing, energy, PPA or an oracle of kernel rereads. Charge baseline L2, GQA/head sharing and prefix aliasing before incremental added-SRAM savings. Report read-fill traffic separately from requested miss payload; pinning is not free coherence/residency control. Shared-prefix logical benefit is not a measured implementation of cross-request prefix caching. Byte accounting must remain consistent when changing granularity.

Follow `trace_collection.md`: bridge whole-model 2–3 decode forwards establish the full weight inter-step stream; partial layers cannot establish whole-model cache residency. Collect actual eager-vLLM traces after the semantic HF bridge; HF SDPA alone is not the optimized-kernel simulation baseline. Collect early/middle/late layers for larger models and bounded full-model traces only after measured storage/runtime budgets permit. TMA descriptors, WGMMA, mbarrier and register values must survive traced kernel coverage/postprocessing/parser validation. Opcode presence and semantics are calibration gates, not assumed from a Hopper tag.

Before rental termination: verify nonempty capture, grouped traces, a positive actual sm_90 replay, archive and transferred SHA256 checksums, local source/runtime/config/model revisions and GPU/profiler metadata. Simulator `gpu_tot_sim_insn` counts active-thread instructions; NVBit reports warp instructions. Convert using actual active masks before comparing; never equate counts or multiply every warp by 32. Preserve parser errors, watchdog/replay caps and semantic gaps. Upstream aggregate validation claims do not validate these decode kernels.

Deliver environment/assumptions/plan/log, schema-complete measured rows, filtered kernel counters, SASS evidence, trace/export manifests, analytical sensitivity curves, calibration table, negative regimes and opportunity report. Recommend an architecture only if realistic incremental savings or movement/MLP opportunity survives the gates. No fixed-area, lower-energy or cycle-accurate architecture claim follows merely from completing this software collection.
