Memory at Fixed Bandwidth

Can more on-chip memory improve serving without increasing off-chip bandwidth?

Yes, if it reduces critical off-chip traffic or improves bandwidth utilization; added capacity without useful reuse can give no gain.

This page models a fixed-batch decode step. Its numbers illustrate the rule; they are not H100 measurements.

What you already know

Each decode step uses model weights and historical keys and values, called KV. On-chip storage can serve repeated reads. The data still must reach the executing threads.

Traffic counts bytes that cross an interface during one measured interval.
Bandwidth ℬ
Bandwidth counts delivered bytes per second. Peak and achieved bandwidth can differ.
Fixed traffic
D_fixed counts reads and writes that the proposed memory change does not reduce.
Reusable traffic
D_reuse counts requested reusable bytes per step, before accounting for cache hits.
Hit fraction h
h counts the byte fraction of those requests served on chip. It is not automatically a cache-counter hit rate.
Capacity C
C counts usable storage dedicated to retention. W is the reusable working set’s size.
Compute F
F counts operations per step. C_compute counts effective operations per second.
Batch B
B counts requests advancing together. A complete ordinary decode step generates B tokens.

The problem

A larger tile can still read every required KV element. A larger cache can evict KV during intervening weight reads. Capacity helps traffic only when needed data remains resident.

The first fill still costs an off-chip read. We analyze later steps with established residency.

How it works

Separate unchanged traffic from traffic that retention can reduce. Before the change, the reusable byte-hit fraction is h₀. Afterwards it is h₁.

Off-chip traffic before and after

D0=Dfixed+(1−h0)Dreuse,D1=Dfixed+(1−h1)Dreuse

The requested reusable bytes need not equal the working-set size. A data element may have several requests. Actual traces and counters establish that distinction.

Fixed-bandwidth memory service

T0≈D0ℬH,T1≈D1ℬH

Memory-limited speedup

T0T1≈Dfixed+(1−h0)DreuseDfixed+(1−h1)Dreuse

The bandwidth cancels from this ratio. When h₁ increases, the numerator’s traffic stays fixed while the denominator’s traffic falls. This predicts speedup only while off-chip service remains the limiting cost.

Ideal dedicated residency

h(C)=min(CW,1)

This ideal policy retains selected data without eviction. Ordinary cache replacement can perform worse. Existing cache hits must be included in h₀ before claiming incremental savings.

Try it

The illustrative batch step reads 64 GiB of weights and requests 8 GiB of KV. The baseline fetches all 72 GiB off chip. Change only dedicated KV capacity.

Predict first: if all 8 GiB KV becomes resident, can this entire batch step become twice as fast from traffic reduction?

No. The unchanged 64 GiB weight traffic remains. The HBM-service ratio reaches 72/64 = 1.125× under the stated assumptions.

Traffic falls from 65 to 64 GiB. The HBM-service ratio is 65/64 ≈ 1.016×. Complete KV retention can still have a small whole-model effect.

What it buys, and what it costs

Other limits can stop the gain

T≈max(FCcompute,DHℬH,DPℬP,Tother)

This simplified bound assumes substantial overlap. D_P counts persistent-storage deliveries and ℬ_P their bandwidth. T_other covers additional limiting work. Removing HBM pressure can expose a compute or on-chip-delivery limit.

fixed-batch decode throughput = B / step_time

More registers or shared memory may improve utilization without reducing bytes. Let η be the achieved fraction of peak bandwidth:

Same peak bandwidth, different utilization

T≈DHηℬpeak

If η increases from 0.5 to 0.75 with unchanged traffic, this service model improves by 0.75/0.5 = 1.5×. That is a utilization gain, not higher peak bandwidth.

If both sources have equal bandwidth and their deliveries serialize, the earlier two-source model gives:

Equal bandwidth under serialized service

s=1(1−f)+fρ=1when ρ = 1

Here f is the retained fraction and ρ is on-chip/off-chip bandwidth. Independent concurrent paths can behave differently. An unchanged shared downstream bottleneck can also prevent gains.

For fixed-area designs, reduced compute must still sustain the faster data supply. For energy, avoided off-chip costs must exceed added storage, fabric and leakage costs.

A common misconception

Doubling on-chip capacity doubles serving performance.

Capacity changes performance through retention, scheduling or data reuse. Without a change in critical traffic or utilization, the bandwidth-limited time stays the same.

Recap

  • Hold off-chip bandwidth fixed and measure the traffic change.
  • Account for existing hits and unaffected weight traffic.
  • Check on-chip delivery, utilization and compute limits.
  • Validate full-step latency and throughput separately from kernel traffic.

Assumptions and limits

  • The 64/8 GiB example is illustrative, not a measured larger-model result. It assumes one unchanged weight stream per batch step.
  • All traffic/time equations require explicit boundaries. Aggregate sector-hit counters cannot directly supply h₀ or h₁.
  • The retention widget omits cold fill, new KV writes, eviction, overlap and retention-management overhead.
  • Real serving mixes prefill, decode, scheduling and variable requests. B/T describes the controlled decode case, not queueing latency.
  • No H100 architecture speedup, area saving or energy benefit follows from these analytical ratios.
