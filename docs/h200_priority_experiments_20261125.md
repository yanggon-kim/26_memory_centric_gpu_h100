# H200 measurement queue for an interruptible rental

Owner assignment, 25 November 2026. Work on `codex/h200-phase01`. The owner's execution prompt activates this queue on the GPUs assigned to this rental. Use [AGENTS.md](../AGENTS.md) for the existing scientific gates. The table below sets the order for new measurements. The deliverable is a Hopper-specific curve of token latency versus available SMs, an explanation of how delivered memory service changes along it, and a test of whether the result survives tuned serving. A null result or a boundary different from AMD is a successful measurement.

## Start and resume

The bridge B1/C1024 eager comparisons at 104/72/40 SMs and restricted native streaming runs are useful checks. The target here is optimized Qwen2.5-32B BF16 and live serving. Keep H100, H200 and RTX measurements distinct.

Inventory allocated UUIDs, topology, free HBM, runtime, profiler permissions, storage and actual remaining rental time. Start a dated run root under h200/ with a case manifest and a Markdown results log. Record the script/config commit, model revision, device, engine, kernel path, seed, effective settings and commands. Prior H200 used vLLM 0.22.1 and PyTorch 2.11.0. Record and qualify any version change. Use the owner's allocated GPUs for the listed single-device, paired, quad and optional TP tests. System changes, extra rentals and changes to clocks, power or MIG remain outside this assignment.

Select the highest-priority unfinished row that fits the available devices and has its prerequisites. Use spare GPUs for independent high-priority cases. Anchor comparisons on the same physical GPU and pair by acquisition; keep device-specific results visible. If a paired job cannot run on a one-GPU rental, mark it deferred and execute the next eligible single-GPU row. If a GPU disappears, resume incomplete acquisitions in a fresh identified cohort. With four devices, finish the core SM curve before occupying the whole node for worker ratios.

Estimate case time from a pilot. After each complete comparison or small bundle, persist results, status and limitations, commit and push. Reserve time for transfer and verify the remote SHA. If budget becomes short, finish a complete comparable curve or contrast before expanding the matrix. Leave a ready-to-run command for the next case. Progress labels are pending, running, complete, partial, blocked or deferred. A pending row is never counted as evidence.

## Queue in priority order

GPU counts below are simultaneous minima per comparison. Additional GPUs can shorten independent sweeps.

|---|---:|---|
| P0 | 1 | **Baseline and restriction proof.** Establish correct optimized full-device 32B decode and a clean eager reference. Verify requested versus granted SMs, device/context/stream used by real decoder kernels through graph capture and replay, kernel mapping and timing. A native proof kernel is a control. Smoke known-byte DRAM reads/writes, matched streaming service, ranges and event intrusion. With two devices smoke P2P/NVLink and a real KV handoff early while keeping P1 first for production. |
| P1a | 1 | **First complete NVIDIA curve.** Start at batch 1, context 4096, one model and fixed outputs after the prefill barrier. Target approximately 100/85/75/60/45/30% of visible SMs using supported granularities. Save actual counts and both unrestricted stock and full-allocation restricted-path controls. Interleave full references to detect drift. Publish the complete measured curve before adding another workload. |
| P1b | 1 | **Find where the curve changes.** Repeat at widths 8 and 32, then a feasible 16K–32K resident context with comparable short-context controls. Refine between adjacent levels near a transition and retain nonmonotonic results. For every shape report clean ms/tick, tokens/s, output agreement, clocks, uncertainty and the smallest tested count demonstrated within 5%, 10% and 25% of full latency using upper confidence bounds. Record censored or unresolved thresholds. |
| P2a | 1 | **Why does latency change?** At full SMs and both sides of an observed slowdown, join NCU physical DRAM reads/writes and L2 traffic to the same workload and clean timing scope. Record useful FLOPs, achieved GB/s, bytes/token and same-allocation stream/gather service. Inspect GEMV/GEMM, attention, occupancy, issue, stalls, grid/tails and outstanding-request proxies where validated. Include kernel-grid retuning at a representative transition and an identical-settings control. Report what the observation point actually measures. |
| P2b | 1 | **Memory-service perturbation.** On owned disjoint SM partitions compare fixed decoder placement with idle, arithmetic and measured streaming doses. Prove placement and overlap, repeat a selected short/long decode and mixed step, log competitor throughput and clocks. A loss under contention motivates modeling effective bandwidth. Quantifying above-stock improvement requires separate validation. |
| P3a | 1 | **Colocated guardrail.** Replay matched decode-only, prefill-only and mixed iterations; vary prompt chunks at fixed decode width and contexts. Locate the 5% headroom boundary. Compare whole/separate, chunked/separate and chunked/mixed policies for decode-heavy and balanced open-loop requests. At full and near-boundary SM counts use identical settings and independently tuned budgets; judge on held-out arrivals. Record actual scheduler composition, queue growth, goodput, TTFT, inter-token tails and energy. Whole/separate and mixed policies must be verified from step records. |
| P3b | 2 | **Dedicated decode worker under load.** Keep prefill full. Compare full and boundary decode allocations with real KV transfer, sufficient KV space and a recorded seat limit. Use at least a light and near-capacity rate, enough requests to distinguish steady operation from drain, and shared absolute SLOs. Report throughput and token latency separately, both boards' energy, queue depths, peak KV, preemptions, link bytes/time and output agreement. A flat rate with a saturated prefill worker gives a bound on decode capacity. |
| P4a | 1 | **Long-prompt cost and kernel attribution (AMD L1/L2).** Compare the same cold prompt whole and in 256/1024/4096-token budgets at 1K, 8K, 16K and 24K–32K where supported. | P4b | 1 | **Long-output tails and memory service (L3/L4).** Sweep 512/2048/4096 output tokens; inject a short or long prompt after first output. ## When optimized SM restriction fails

Investigate autonomously. Check actual SM granularity, worker processes, context inheritance, library streams, graph capture, kernel launch contexts and output stability. Try a bounded versioned repair and a small paired pilot. Log the failure immediately. If a trustworthy optimized restricted path remains unavailable, **collect and publish the restricted eager curve under its own label**, with same-engine full eager controls. Report optimized full-device timing separately. If eager restriction also fails, retain the diagnostics and any verified native allocation/service curve.

**Use the remaining rental for eligible full-GPU traffic and scheduler measurements.** Prioritize P2a physical counters on optimized full-device decode, P3a tuned serving and P4 long-context work. Two devices can still run full-worker P3b/P5a comparisons. Track restricted comparisons as blocked and run independent cases. Apply the same principle when counter permissions, memory capacity, topology or archive access limit one measurement.

## Limitations, checkpoints and delivery

Maintain [the H200 limitations register](h200_measurement_limitations_20261125.md) **during execution**. On discovery, add a dated entry there and a short note next to the affected comparison in the run's Markdown results log. Record command/config, requested and achieved scope, evidence/log path, consequence for interpretation, attempted remedy, fallback result and resume condition. Update entries when resolved and preserve earlier failed attempts. Include data-quality limitations as well as crashes, such as uncaptured launches, clock drift, finite trace ceilings, unavailable HBM counters, unmatched outputs, prefill bottlenecks and co-tenant interference.

Preserve existing quantitative gates and label early pilots separately. For clean timing use the branch's acquisition/clock/isolation rules. For stochastic serving use paired independent trace seeds and record request-level SLO definitions and completeness. Capture raw counter/energy data separately from uninstrumented timing; used/allocated KV, logical demand and physical DRAM bytes have different units or meanings. An SM cut restricts a bundle of resources and releases no physical die area on this machine.

Return the remote commit SHA, per-row disposition, actual GPU-hours, result/report paths, raw checksums, and exact next command. Lead the report with the NVIDIA curves, physical service evidence and serving consequences. Compare against AMD only after deriving the H200 thresholds independently.
